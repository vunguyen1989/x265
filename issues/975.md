# PR #975: Recon file fixes

Nguồn: [Multicorewareinc/x265#975](https://github.com/Multicorewareinc/x265/pull/975)

## Phạm vi

PR này sửa các lỗi khi xuất reconstructed picture qua `--recon`. Thay đổi chỉ nằm ở writer Y4M/YUV và cách CLI khởi tạo writer; không thay đổi thuật toán encode hoặc nội dung bitstream HEVC.

PR xử lý ba lỗi chính:

1. Y4M 10/12-bit bị ghi đè dữ liệu khi offset vượt 4 GiB.
2. Downshift reconstructed Y4M từ 10/12-bit xuống 8-bit hoạt động sai.
3. Raw YUV high-bit-depth bị ghi sai trong cấu hình multilib.

## Finding 1: Offset của Y4M high-bit-depth bị overflow 32-bit

### Code cũ

```cpp
outPicPos += (uint64_t)(pic.poc * (6 + frameSize * 2));
```

Mặc dù kết quả được cast sang `uint64_t`, phép nhân bên trong ngoặc đã được thực hiện bằng kiểu 32-bit. Khi offset vượt `UINT32_MAX` (xấp xỉ 4 GiB), giá trị bị wrap trước khi được chuyển sang 64-bit.

Y4M writer xác định vị trí ghi từ POC:

```text
offset = headerSize + poc * (frameHeaderSize + framePayloadSize)
```

Vì vậy offset bị wrap sẽ khiến writer seek về một vị trí trước đó và ghi đè lên các frame đã có. File recon sau mốc này bị corrupt.

Nhánh 8-bit đã cast `pic.poc` trước phép nhân nên không gặp đúng lỗi này. Lỗi nằm ở nhánh high-bit-depth, nơi mỗi sample chiếm hai byte.

### Cách PR sửa

```cpp
outPicPos += static_cast<uint64_t>(pic.poc) * (6 + frameSize * 2);
```

Cast được thực hiện trên một toán hạng trước phép nhân, nên toàn bộ phép tính offset diễn ra ở 64-bit.

### Mức độ ảnh hưởng

Lỗi có thể xuất hiện khá sớm với video độ phân giải cao. Một frame 4K YUV420 10-bit chiếm gần 25 MB, nên offset có thể vượt 4 GiB sau khoảng 173 frame, tương đương chưa đến 6 giây ở 30 fps.

## Finding 2: Y4M dùng sai bit-depth để chọn cách đọc reconstructed buffer

Code cũ trộn lẫn ba khái niệm khác nhau:

- `sourceBitDepth`: bit-depth của file input ban đầu.
- `pic.bitDepth`: bit-depth thật của reconstructed buffer do encoder trả về.
- `bitDepth`: bit-depth được yêu cầu cho file recon, tức `--recon-depth`.

`sourceBitDepth` không xác định kiểu dữ liệu của reconstructed picture. Ví dụ:

```text
input:          8-bit
encoder:       10-bit
recon output:   8-bit
```

Trong trường hợp này, reconstructed buffer vẫn chứa các sample `uint16_t`, vì nó được tạo bởi encoder 10-bit. Nếu writer nhìn vào input 8-bit và đọc buffer như dữ liệu 8-bit, output sẽ sai.

Code cũ dùng `inputDepth/sourceBitDepth` để chọn nhánh xử lý. Điều này có thể dẫn đến:

- Không thực hiện downshift dù file recon được yêu cầu là 8-bit.
- Ghi sample 16-bit vào payload nhưng header Y4M khai báo 8-bit.
- Đọc reconstructed plane bằng sai kiểu con trỏ.
- File có kích thước và layout không khớp với header.

### Cách PR sửa

PR phân tách rõ trách nhiệm:

```text
pic.bitDepth -> kiểu và độ sâu thật của buffer trong RAM
bitDepth     -> định dạng cần ghi ra file
```

Khi buffer high-bit-depth cần được xuất thành 8-bit:

```cpp
if (pic.bitDepth > 8 && bitDepth == 8)
{
    int shift = pic.bitDepth - 8;
    // Đọc bằng uint16_t* và ghi src[w] >> shift.
}
```

Writer đồng thời phát warning ở frame đầu tiên khi thực hiện downshift.

## Finding 3: Raw YUV high-bit-depth bị hỏng trong multilib

### Nguyên nhân

YUV writer cũ quyết định cách xử lý bằng macro compile-time:

```cpp
#if HIGH_BIT_DEPTH
    // Đọc reconstructed plane như uint16_t.
#else
    // Đọc reconstructed plane như char.
#endif
```

Cách này không đúng trong cấu hình multilib. Một cấu hình phổ biến là:

```text
CLI/base library được build 8-bit
encoder library 10/12-bit được chọn ở runtime
```

Khi đó `HIGH_BIT_DEPTH` của CLI là false, nhưng encoder được nạp động vẫn trả về reconstructed picture có `pic.bitDepth` bằng 10 hoặc 12 và các plane chứa sample `uint16_t`.

Writer cũ vẫn đi vào nhánh 8-bit và đọc plane như `char*`. Hậu quả là raw YUV recon có byte layout sai, kích thước sai hoặc hình ảnh bị corrupt.

### Cách PR sửa

PR bỏ lựa chọn bằng `#if HIGH_BIT_DEPTH` và chuyển sang kiểm tra runtime:

```cpp
if (pic.bitDepth > 8)
{
    // Đọc plane bằng uint16_t*.
}
else
{
    // Đọc plane bằng char*.
}
```

Nhờ đó writer sử dụng bit-depth của encoder thực sự đang chạy, thay vì bit-depth của CLI/base library tại thời điểm compile.

Logic runtime mới cũng hỗ trợ downshift reconstructed 10/12-bit xuống file YUV 8-bit và phát warning tương tự Y4M.

## Finding 4: `sourceBitDepth/inputDepth` là dependency sai trong output writer

Sau khi sử dụng `pic.bitDepth` làm nguồn thông tin về reconstructed buffer, `sourceBitDepth/inputDepth` không còn cần thiết trong:

- `ReconFile::open`
- `Y4MOutput`
- `YUVOutput`
- Lời gọi từ CLI khi khởi tạo recon writer

PR loại bỏ tham số và member này. Đây không chỉ là cleanup: nó loại bỏ dependency sai đã dẫn đến việc writer suy luận kiểu reconstructed buffer từ bit-depth của input.

## Các thay đổi không ảnh hưởng hành vi chính

Commit cuối của PR chủ yếu:

- Thay C-style cast bằng `static_cast` và `reinterpret_cast`.
- Chuẩn hóa indentation.
- Viết lại một số biểu thức cast cho rõ ràng hơn.

Các thay đổi này phục vụ code style; phần sửa hành vi nằm ở phép tính offset 64-bit và việc chọn đường xử lý theo `pic.bitDepth` tại runtime.

## Giới hạn còn lại

PR không triển khai conversion bit-depth tổng quát. Các trường hợp được xử lý hợp lý là:

- 8-bit buffer sang recon 8-bit.
- 10/12-bit buffer sang recon 8-bit bằng downshift.
- 10/12-bit buffer sang recon có cùng bit-depth bằng cách ghi nguyên sample 16-bit.

Các tổ hợp như 8 -> 10, 8 -> 12 hoặc 12 -> 10 không được chuyển đổi đầy đủ. Một số mismatch chỉ được bảo vệ bằng `X265_CHECK`; macro này không hoạt động trong release build thông thường. Vì vậy CLI vẫn nên validate và từ chối rõ ràng các tổ hợp `--recon-depth` không được hỗ trợ nếu muốn tránh output sai âm thầm.

## Kết luận

Hướng sửa của PR là đúng về mặt thiết kế:

- Dùng `pic.bitDepth` để xác định representation của reconstructed buffer.
- Dùng `--recon-depth` để xác định representation của file output.
- Không dùng `sourceBitDepth` hoặc `HIGH_BIT_DEPTH` của CLI để suy luận dữ liệu do encoder runtime trả về.
- Thực hiện phép tính file offset ở 64-bit trước khi giá trị có thể overflow.

PR sửa các lỗi corruption thực tế của recon output, đặc biệt với file Y4M lớn và cấu hình multilib 8/10/12-bit.
